# References on documentation for agents

Consulted while shaping this template's documentation policy. Kept apart from the decisions so that each decision stays about the module structure it governs.

Research available by 2026-09-30 gives no universal optimum for agent documentation. [Gloaguen et al. (2026-02-12, v1)](https://arxiv.org/html/2602.11988v1) found higher costs and limited task-success gains from repository context files in predominantly Python tasks. [Lulla et al. (2026-01-28, v1)](https://arxiv.org/html/2601.20404v1) found lower runtime and output-token use in a different experiment, without comprehensive functional-correctness evaluation. Neither validates this Flutter structure. Keep global instructions minimal, load module contracts when relevant, and assess correctness alongside effort.

[Flutter architecture recommendations](https://docs.flutter.dev/app-architecture/recommendations) recommend separating UI and view-model responsibilities while making a domain layer conditional on complexity. [Repo0 (2026-08-20, v1)](https://arxiv.org/html/2608.19854v1) studied generation of six Python repositories: unconstrained model-directed structural evolution tended to over-decompose the architecture and reduce downstream correctness. This supports caution about automatic extraction, not a claim of Flutter-specific evidence or an optimal number of modules.

[Probe-and-Refine (2026-06-19, v2)](https://arxiv.org/html/2606.20512v2) found improved issue resolution from guidance refined against observed probe failures in its main model/harness, without a corresponding precision gain or a successful cross-model replication. [Compact Documentation (2026-09-25, v1)](https://arxiv.org/html/2609.31587v1) found no significant benefit from file summaries when source was already available, with model and task-selection limits. These results favor evaluating useful operational knowledge rather than assuming that more documentation helps. Neither validates this Flutter template.
